# Starling architecture

Owned by the Orchestrator. Lanes read this and `docs/BRIEF.md` before doing anything. Decisions and their sources live in `docs/decisions/`; this file describes the system as it stands.

Status: **v2 interfaces (Phase 1.5).** Last updated 2026-09-30. v1 added identity, pairing, the shared hard-limit check, and the Down facade (section 7). v1.1 (from lane G's requests) added `Answer.issue`, local `OutboundContext` passed to the policy, `OutboxObserver`, and a policy re-check after consent. v2 turns features into skills (section 8, ADRs 0010 to 0018): skill descriptors, registry and flags, one interaction lifecycle, artifacts and chaining, global privacy topics, skill-aware agent cards, and envelope version 1.

## 1. Layers and packages

```
App (SwiftUI, generated by XcodeGen from App/project.yml)
  │   one lifecycle coordinator: every SkillService's events → Interaction store → shared screens
  │
  ├── Skills/DownFor, Skills/FindATime, Skills/PickAPlace, Skills/SwapPhotos   one package per skill (v2)
  ├── StarlingChaining      chain suggestions, time-triggered chains, per-link consent, timeline and audit (v2)
  │
  ├── StarlingDesign        UI only: the live status mark and brand palette; imports no Starling package
  │
  ├── StarlingNegotiation   building blocks: aggregation, mutual reveal, query, bargaining, exchange
  ├── StarlingAgent         FoundationModels implementation of AgentModel; owns every prompt
  ├── StarlingPolicy        PolicyEngine implementation, consent sheet model
  ├── StarlingAvailability  EventKit, stated intent, ask-owner sources
  ├── StarlingIdentity      keys, pairing, pinned peers, secure channel (Transport decorator)
  ├── StarlingTransport     Loopback, LocalP2P, WiFiAware, Relay
  │
  └── StarlingCore          protocols, message types, IDs, Outbox, Inbox   (Foundation and CryptoKit only)
        └── StarlingFakes   deterministic doubles for tests (second product of the same package)
```

Every box is its own SwiftPM package under `Packages/` with one owning lane (ADR 0006). Everything below `StarlingDesign` depends on `StarlingCore`; nothing else depends sideways without Orchestrator approval. `StarlingDesign` is app-side UI and depends on no other Starling package, so the app maps feature state (for example `DownEvent`) to its `MarkState` (ADR 0172).

Platforms: iOS 27.0 for the app; packages also declare macOS 26.0 so `swift test` runs on the host (ADR 0001).

## 2. Message flow

```
feature ──► Outbox ──► PolicyEngine ──► ConsentProvider ──► EnvelopeCodec ──► [SecureChannel] ──► Transport ══► peer
                        (deny / allow /    (only when policy     (JSON v0,          (Phase 1,           (opaque
                         needsConsent)      asks)                  size-capped)      ADR 0003)           frames)

peer ══► Transport ──► [SecureChannel] ──► Inbox ──► feature
                                           (decode, validate, recipient and sender
                                            checks, age window, replay window)
```

Rules that hold everywhere:

1. **Outbox is the only way to send.** Features never hold a `Transport` for sending. This is how "no data leaves a device without passing through the policy layer" is enforced structurally, not by convention.
2. **Inbox is the only way to receive.** Features consume `InboxEvent`, never raw `TransportEvent`.
3. **Transports do not authenticate.** A `PeerID` from a transport is a claim. The Phase 1 secure channel is a decorator that conforms to `Transport`, verifies peers against keys pinned at pairing, and encrypts frames; nothing above or below it changes.
4. **The model never decides egress.** `PolicyEngine` is deterministic.
5. **Delivery is best effort.** `Transport.send` succeeding means the frame reached the link, not the peer's app. Negotiation must survive lost messages with timeouts and idempotent retries.
6. **The model proposes; code enforces.** Hard limits (budget, availability, avoided items) are checked in code before and after every model call. The Phase 0 bench measured the model accepting proposals that broke hard limits (`docs/research/model-budget.md`).
7. **No free text crosses the wire.** Peers send typed, bounded values (`Keyword`, `TimeSlot`, `MoneyAmount`, flags, counts). The only peer data a model may see is those values (ADR 0009). The one exception is a venue's `PlaceName` (v2): bounded display text that stays out of prompts until lane D designs for it (ADR 0012).
8. **A peer's message never starts anything.** An incoming envelope creates at most an invitee interaction. It never starts a skill, requests a permission, or skips Consent on the receiving phone, even with `chainedFrom` set (ADR 0012).

### Wire format v1

One envelope per frame, sorted-key JSON. Version 1 (v2 interfaces) adds the optional `skill` and `chainedFrom`:

```json
{"body":{"type":"propose","value":{"round":0,"terms":{"budget":{"amount":{"currency":"USD","minor":1500},"type":"amount"}}}},
 "chainedFrom":"<uuid>","conversation":"<uuid>","id":"<uuid>","recipient":"<64 hex>","sender":"<64 hex>","sentAt":<ms since 1970>,
 "sequence":0,"skill":{"id":"pick_a_place","version":"1.0"},"version":1}
```

Version 0 frames (Phase 1 builds) still decode, with neither field; a version 0 envelope that claims a skill or chain is rejected. Phase 1 builds reject version 1.

Time slots are whole minutes since 1970 UTC. Changing anything here breaks `EnvelopeCodecTests.wireFormatIsFrozen` on purpose; `phaseOneFramesStillDecode` keeps version 0 working.

## 4. Changing a frozen interface

1. The lane writes the request in `docs/requests/<lane>.md`: what, why, which tests show the need.
2. The Orchestrator decides, updates `StarlingCore` on its own branch, and the owner merges it to `main`.
3. Lanes rebase onto that commit.

Additive changes (a new `IssueKey` constant, a new `Capability`) are cheap. Changes to `Envelope`, `MessageBody`, or any protocol requirement bump `Envelope.currentVersion` or wait for the next phase freeze.

## 5. Testing strategy

| Layer | How it is tested without a device |
|-------|-----------------------------------|
| Core types and codec | Unit tests, golden wire format, hostile-input cases |
| Negotiation, policy, availability | Against `StarlingFakes` and `LoopbackTransport` |
| Multi-party and adversarial | `Tools/Simulator` over Loopback: N agents, scripted peers, a malicious peer |
| LocalP2P | Framing and connection-dedup logic unit-tested; radio behavior on devices only |
| Wi-Fi Aware | Link table, dial race, reconnect, and backoff unit-tested against an in-memory radio; radio behavior on devices only |
| Model | `ScriptedAgentModel` for logic; `StarlingAgent` harness runs the real model on macOS 26.7+ hosts and on devices |

`Tools/test-all.sh` runs every package's tests with warnings as errors. CI runs it on the `xcode-27` runner (ADR 0007).

Every lane ends with a device checklist: short, numbered, specific.

## 6. Security status

Phase 0 is **unauthenticated and unencrypted** on every transport. Do not send real personal data over it. ADR 0003 (accepted 2026-09-30) specifies the Phase 1 secure channel and the care requirements it must meet. No privacy claim ships before `docs/THREAT_MODEL.md` exists.

Known Phase 0 limits, recorded so the threat model picks them up:

- `Inbox` replay state is in memory and bounded; a replay after an app restart is caught only by the age window.
- `ModelLocality` is self-declared (brief open question 4).
- `InsecurePSIStub` reveals the initiator's set to the responder.
- A `Keyword` of up to 32 letters can still carry an instruction-like phrase ("ignore all previous rules"). The defenses are structural: the model sees keywords as schema data, its outputs are typed moves, and it never decides egress. Lane I tests this.

## 7. Down? v1 flow (baseline for lane F)

Lane F owns the details and may request message changes through `docs/requests/F.md`. This is the contract the other lanes build against.

1. **Intent.** The owner types something like "free tonight, want food, under $15". `AgentModel.interpret` turns it into `OwnerRules`, the owner reviews and edits them, and the app calls `DownService.setIntent` with a `DownLevel` (`down` or `maybe`) and an expiry.
2. **Who.** Only paired friends reachable over the secure channel, so every sender is authenticated. No unpaired peer ever receives Down traffic.
3. **Mutual interest first (PSI).** Each PSI send passes `OutboundContext.psi` (provider and typed inputs) so the policy can judge it. Each side builds a small set of tokens from its time windows (for example 30-minute slots inside the intent, capped by `PSIConfiguration.maxPeerSetSize`). `down` and `maybe` produce the same tokens, so the PSI run does not reveal the level. An empty intersection ends the exchange silently on both phones.
4. **Details, only after overlap.** `query`/`answer` over activity keywords and budget (every `Answer` names its issue, v1.1). The receiving agent fuzzy-matches with `AgentModel.match`. Every send goes through `Outbox`, so policy and consent apply (the PSI stub is not private, so policy requires consent while it is in use).
5. **Agree.** `propose`/`counter`/`accept`, with hard limits checked in code before and after every model call (rule 6).
6. **Notify.** Only after both sides have sent `accept` does `DownEvent.matched` fire, on both phones. Whether each side was `down` or `maybe` is exchanged only at this point, so a "maybe" is revealed only when interest is mutual.
7. **Silence on failure.** Every step has a timeout (delivery is best effort, rule 5). Timeouts, rejections, and withdrawn intents end without an event, so one-sided interest never notifies anyone.

## 8. Skills (v2, Phase 1.5)

Down for…, Find a time, Pick a place, and Swap photos are skills on one platform (ADR 0010). Each skill package provides a `SkillDescriptor` (data), a `SkillService` (runtime over the app's one Outbox and Inbox), and model hints the `SkillModel` uses (ADR 0016). Section 7's flow becomes the Down for… skill's flow, reported through the shared lifecycle:

1. **Compose.** The owner types in New. `SkillModel.route` picks a skill that can run (`SkillRegistry.available`), and `SkillModel.intent` reads the chips, which the owner edits. Peers that do not support the skill are left out with a clear message (`AgentCard.support(for:)`).
2. **Consent.** Every send goes through `Outbox` with the skill's `SkillRef`; the policy applies the owner's privacy topics (ADR 0014) and asks when needed. The lifecycle shows a pending consent under Needs you.
3. **Negotiate, Propose, Confirm.** The service reports `InteractionEvent`s; the coordinator applies them to the state machine (ADR 0011) and Home shows the result.
4. **Hand off and Remember.** A confirmed plan becomes a `Plan` artifact; "Keep it going" offers chains the group supports (ADR 0012), each with a fresh Consent if it adds a topic or permission; hand-offs open Calendar, Messages, or Maps with the owner in control (ADR 0018). The interaction's history and egress log feed the plan's timeline and "What left your phone".
