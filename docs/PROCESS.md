# How this was built

Starling was built from 2026-09-29 to 2026-10-05 by one developer (called "the owner" throughout the docs) directing several AI coding agents in parallel. This document describes how that work was organized, what the checks caught, and what went wrong, with links to the records behind each claim.

## Roles

- **The owner** set direction, approved each phase's lane plan, accepted decisions that changed the brief, ran the device tests on two iPhones, and approved merges.
- **The Orchestrator** was a coordinating AI agent. It wrote the interface freezes in `StarlingCore`, owned the shared docs, answered lanes' requests, and ran the merge gate.
- **Lane agents** each owned specific directories in their own git worktree and branch. A lane ended with **DONE** (tests passing, ADRs for new decisions, a device checklist) or **BLOCKED** (exactly what it needed, and from whom).
- **Reviewers** were AI models from a different vendor than the one that wrote most of the code: OpenAI's Codex reviewed work written mostly with Anthropic's Claude (the commits carry `Co-Authored-By` trailers). The lane plans give the reasoning: an independent model is a better adversary.

## A change, end to end

1. The owner approves a lane plan: each lane's directories, deliverables, and acceptance criteria.
2. The Orchestrator merges the phase's Core freeze, and every lane branches from it.
3. A lane builds and tests against fakes and the Loopback transport, and writes ADRs for its decisions.
4. Risky pull requests go through adversarial review rounds until every finding is fixed with a test or tracked as an issue.
5. The Orchestrator runs the gate on the branch merged into the current `main`.
6. The owner merges, then runs the lane's device checklist on two iPhones; findings come back as issues.

## Interfaces first: the Core freeze

Parallel agents in separate worktrees still conflict when they edit the same files. Three choices kept that from happening:

1. **One Swift package per lane** ([ADR 0006](decisions/0006-one-swiftpm-package-per-lane.md)), and an app project generated by XcodeGen instead of a committed `.pbxproj` ([ADR 0005](decisions/0005-xcodegen-for-the-app-project.md)).
2. **A freeze before every phase.** The Orchestrator wrote the protocols and message types in `StarlingCore` and merged them before any lane started: v0 (#1), v1 (#3), v2 (#45, after five adversarial review rounds). Lanes built against `StarlingFakes`, so nobody waited on another lane's code.
3. **Request files instead of edits.** A lane that needed an interface change wrote what, why, and which test showed the need in its request file. The Orchestrator answered in the same file and changed Core on its own branch. The [15 request files](requests/README.md) record each ask and answer, for example how P15-A's question about who reports consent events became [ADR 0011](decisions/0011-one-lifecycle-and-interactions.md) amendment 15.

Fixes several lanes needed went into Core once. The final reviews of three skill pull requests (#53, #55, #56) found each skill's own record of what a friend had been told leaking at a different edge: a ledger kept for only 24 hours, a cache a peer could evict, a budget a relaunch refilled. The fix became one persistent conversation ledger enforced by `Outbox` ([ADR 0021](decisions/0021-one-ledger-for-what-a-friend-was-told.md)).

## Decisions as ADRs

Every decision with a trade-off is an ADR with primary sources (Apple documentation, specifications, source code). Each lane wrote ADRs in its own number range, so parallel lanes never edited the same file; the Orchestrator indexed them on merge. Decisions that changed the brief waited for the owner. When a later finding changed a decision, the ADR was amended in place with a numbered amendment, so the reasoning stays traceable (for example, [ADR 0011](decisions/0011-one-lifecycle-and-interactions.md) amendments 13 to 17).

## Adversarial review

Pull requests that touched security, protocols, or concurrency were reviewed by an AI model instructed to find defects. The implementing lane fixed each finding with a regression test that reproduced it first, then asked for another round. These are automated reviews, not an independent security audit, and no independent audit has taken place ([THREAT_MODEL section 6](THREAT_MODEL.md#6-review-history)).

The secure channel (#16) took six rounds and 17 findings. Phase 1.5 lane pull requests took two to five rounds each. Examples of what the reviews caught:

1. **Unpairing raced the handshake.** Four rounds in a row found a new await where an unpaired friend could still be heard. The fourth asked for a redesign instead of another patch. Revocation now goes through one `PinAuthority` that stamps every session with an epoch and checks it in the same lock section that seals or delivers each frame ([ADR 0100](decisions/0100-noise-secure-channel-implementation.md) decision 11).
2. **A silent restart let a phone in the middle retry the pairing code.** After the codes failed to match, the middle phone could send a new hello and the victim would restart unseen with a fresh nonce: a new code to try every two round trips. Now a ceremony gives out one nonce, so one code, per visible failure ([ADR 0260](decisions/0260-pairing-that-works-on-the-first-try.md), round 3 of #104).
3. **Two plan changes at once could leave phones on different plans.** Both changes named the same revision, everyone said yes to both, and phones applied them in different orders. The revision check catches a stale change but cannot choose between two fresh ones, so a phone now takes part in one change per plan at a time ([ADR 0023](decisions/0023-one-change-to-a-plan-at-a-time.md), second review of #118).
4. **A quiet group ask leaked who was interested.** Four rounds of #56 found leaks through rosters, coupled schedules, and candidate caps. Instead of a fifth patch, quiet asks became one-to-one, and a group plan became an explicit invite ([ADR 0210](decisions/0210-down-for-one-friend-at-a-time.md)).
5. **Change the plan diverged after failures.** Five rounds of #111 found a lost confirmation, a leave racing a change, a friend added while someone leaves, and a crash mid-commit. Confirmations, leaves, and withdrawals are now acknowledged, resent, and journaled ([ADR 0243](decisions/0243-change-the-plan.md)).

## The red team

The red-team lanes (I in Phase 1, P15-F in Phase 1.5) owned only `Tools/Simulator/Scenarios/` and test targets. They never edited product code. For each defect they filed an issue with a reproduction; the owning lane fixed it, and the reproduction stayed as a regression test ([ADR 0150](decisions/0150-adversarial-test-method.md), [ADR 0250](decisions/0250-phase-1-5-adversarial-contracts.md)).

Examples:

- **A friend's fast reply was dropped (#105).** Pick a place recorded a query's ID only after `Outbox.send` returned, but a reply could arrive before that. It was dropped as unsolicited and the plan waited for its deadline. Find a time had the same ordering. Both now hold an authenticated early reply while its own send is in flight and count it only if it names something sent to that friend.
- **Answers naming queries that were never sent (#63, #68)** could advance an organizer. Both skills now check against what they actually sent.
- **The PSI stub accepted replies above its set-size bound, and malformed digests (#6, #7).** The bound is what stops a dishonest peer from submitting every time slot and learning a whole week of free time.
- **The model's negative controls fail (#9).** Paired injection measurements show the on-device model matching "food" to "movie" even without an attack. The issue stays open, marked with known-issue assertions so a partial fix shows up ([results](../Tools/Simulator/Tests/PromptInjectionTests/Results/README.md)).

## Device testing

No agent can hold an iPhone, so every lane ended with a short, numbered device checklist, and a criterion counted as done only after the owner's run on two phones. Two runs found what the simulations had not: pairing failed until about the hundredth try, a button stayed disabled with no reason given, and chips paraphrased the owner's words. Lane P15-G then reproduced eight of nine pairing failure causes over the Loopback transport before fixing them ([ADR 0260](decisions/0260-pairing-that-works-on-the-first-try.md), [Phase 1.5 report](plans/phase-1.5-report.md)).

## Test reliability

Tests that passed alone failed in the gate when many packages built at once. The fixes were about what a test waits for, not longer timeouts:

1. **Virtual time.** Services take an injected clock. A test waits until the service has registered its deadline, then advances the clock to it instead of sleeping ([ADR 0256](decisions/0256-load-tolerant-simulator-waits.md), #86, #110).
2. **Waits on a suspending clock.** Condition waits measure time the test process could actually run, and check the condition once more before declaring a timeout. A false condition at the deadline still fails ([ADR 0258](decisions/0258-simulator-waits-count-awake-time.md)).
3. **Explicit barriers.** Tests wait for an observable event (a skill handled the hello, a journal drained its writes) instead of a fixed sleep ([ADR 0257](decisions/0257-observe-service-completion-in-red-team-tests.md), #125).

One known flaky test remains (#59).

## What went wrong, and what changed

| Problem | Change |
|---|---|
| Patching races one await at a time | After repeated findings of one class, redesign the mechanism (the `PinAuthority` epoch) |
| Privacy designs for group asks kept leaking | Narrow the product: quiet asks are one-to-one until a private group reveal has its own design and review |
| Tests passed while pairing failed on phones | Reproduce device failures over Loopback first; a Debug-only pairing log that never records keys or codes |
| A revision check was trusted to order concurrent changes | One change per plan at a time, shared by every skill that changes a plan |
| Code assumed a send returns before its reply arrives (#105) | Hold early authenticated replies while their send is in flight |
| Hosted CI was not running for most of the project | `Tools/local-gate.sh` runs CI's steps on the merge result in a throwaway worktree, and lane merges recorded the gate result in the pull request |
| Wall-clock waits failed under load | Virtual time, suspending-clock waits, and explicit barriers |
| A Debug-only scripted service blurred a device result | Debug-only behavior is labeled in the app, and the scripted service waits like the real one |

## Glossary

The ADRs, request files, and checklists were written during development and use these terms.

- **Lane**: a parallel workstream run by one AI coding agent in its own git worktree, owning specific directories. Phase 1: BR (brand), C2 (agent quality), E1 (identity and secure channel), E2 (Wi-Fi Aware), F (negotiation), G (policy and consent), H (app), I (red team). Phase 1.5: P15-A (shell), P15-B (Down for... and the model), P15-C (Find a time), P15-D (Pick a place), P15-E (chaining and audit), P15-F (red team), P15-G (pairing reliability).
- **Orchestrator**: the coordinating agent that owned `StarlingCore`, the shared docs, request answers, and the merge gate.
- **The owner**: the project's maintainer, who approved plans and decisions, ran device tests, and approved merges.
- **Core freeze**: a version of `StarlingCore`'s protocols and message types merged before a phase's lanes started. Lanes could not edit it; changes went through request files. Versions: v0, v1, v1.1, v2, v2.1.
- **Gate**: `Tools/local-gate.sh <branch>`, which merges a branch into `main` in a throwaway worktree and runs CI's checks (every package's tests, the app build, the Release checks). "GATE PASS" was the merge condition.
- **Request file**: `docs/requests/<lane>.md`, where a lane asked for a change outside its directories and the Orchestrator answered. "Request P15-E 4.1" means item 4.1 in `docs/requests/P15-E.md`.
- **Device checklist**: `docs/checklists/<phase>-<lane>.md`, the numbered steps a lane left for the owner to run on real iPhones.
- **Codex review**: an automated adversarial code review by OpenAI's Codex agent. Not a human or third-party audit.
- **ADR number ranges**: 0001 to 0099 project-wide; 0100 to 0179 Phase 1 lanes; 0200 to 0269 Phase 1.5 lanes.
