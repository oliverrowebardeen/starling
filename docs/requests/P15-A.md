# Requests from lane P15-A (Shell and IA)

## 1. Confirm who reports consent events (lanes B to E): answered

Resolved by ADR 0011 amendment 15 (Core v2.1, 753ddcf): consent events come from the coordinator only.

### Original request

**What.** The lifecycle coordinator, not skill services, reports `consentNeeded(request:)` and `consentGiven(request:)` (ADR 0201 decision 3). The app's `ConsentProvider` reads `Disclosure.conversation` when `Outbox` asks it, suspends that conversation's interaction under the next request ID above its watermark, and resumes it (or ends it declined) when the owner answers. Skill services should not emit consent events.

**Why.** A sheet appears inside `Outbox.send`, which the service cannot observe, and request IDs only rise, so two sources would collide: the second `consentNeeded` is refused as `UnknownConsentRequest`, or an interaction waits on a request nobody will close. Lane B's kickoff mentions "consent request IDs"; this asks the Orchestrator to confirm the split with lanes B, C, D, and E, as amendment 13 did for `.started`.

**Tests.** `ConsentLifecycleTests` and `AppOutboxTests.everySendIsRecordedOnItsInteraction`.

**Meanwhile.** Built this way. A service that emits consent events anyway gets them applied if their IDs happen to rise, or dropped and logged if not.

## 2. A Release check: no Developer section, no test-build notices

**What.** A CI step (and a `Tools/local-gate.sh` step) after the Release build, in the style of `Tools/check-release-no-fakes.sh`. Proposed `Tools/check-release-no-debug.sh`:

```bash
#!/usr/bin/env bash
# Fails if a Release build contains the Debug-only Developer section or a
# test-build notice (ADR 0015 decision 5, lane P15-A).
set -euo pipefail
root="$(cd "$(dirname "$0")/.." && pwd)"
derived="${1:-$root/.build/app-release}"
binary="$derived/Build/Products/Release-iphonesimulator/Starling.app/Starling"
symbols="$(nm "$binary")"
grep -q StarlingCore <<<"$symbols" || { echo "No StarlingCore symbols; cannot check."; exit 1; }
for name in DeveloperView DebugHarness DemoDriver LifecycleSelfTest DebugPermissionAccess; do
  if grep -q "$name" <<<"$symbols"; then echo "Release contains $name (ADR 0015)."; exit 1; fi
done
for text in "This is a test build" "doesn't hide free times" "scripted services"; do
  if strings "$binary" | grep -qF "$text"; then echo "Release contains the notice \"$text\" (ADR 0015)."; exit 1; fi
done
echo "Release has no Developer section and no test-build notices."
```

It reuses the Release build that `check-release-no-fakes.sh` already makes.

**Why.** ADR 0015 decision 5 and the lane plan's acceptance: Release builds have no Developer section and no test-build notices, guarded by CI. `Tools/` is the Orchestrator's.

**Meanwhile.** Every file in `App/Sources/Developer/` and the Debug composition sit inside `#if DEBUG`; Release passes `EmptyView()` as You's developer slot. I ran the script above by hand against this branch's Release build (result in the PR).

## 3. Skill lanes: what the shell needs from each package (B, C, D, E)

So each skill drops in by filling `AppServices.makeSkills` and `permissions`:

## 5. A journal entry's interaction (lane E): resolved

Lane E's PR #78 journals the interaction, and the app's relay prefers it (branch `phase-1.5/a-relay-interaction`).

**What.** Add the send's `OutboundContext.interaction` to `EgressJournalEntry` (optional, like `skilled`, defaulting to nil for older files), keep it on the recorder's pending send, and pass it to the sink, for example `EgressSink.appendEgress(_:conversation:interaction:)` with a default that drops it.

**Why.** A Down for... member sends in the starter's conversation, but the send belongs to its own request (P15-B request 8). The app now attributes the record by the interaction the send named, which it learns from its own Outbox observer this launch. A send recovered from the journal after a crash carries only its conversation, so the recorder keeps it waiting for an interaction that never arrives, and the member's request can read as complete without it.

**Meanwhile.** Such a send stays pending and journaled, so it is never lost, and its starter's conversation reads as unconfirmed. The member's own request does not know about it until the entry carries the interaction.

## 6. Change the plan: what the shell needs (lane E, ADR 0022): answered

Lane E's PR #111 (ADR 0243, `docs/requests/P15-E.md` items 10 to 14) answers these. Items 3 and 4 are worded in the app, from the owner's nicknames (ADR 0207).


Lane A builds "Suggest a change" and "Leave this plan" on a plan's detail, the incoming suggestion cards, the suggester's waiting card, and the updated hand-offs. It needs these from lane E's Change the plan package. Each item says what the app does with it.

1. **Whether a suggestion can start now.** A pure check like `ChainPlanner.suggestions`, for one plan: confirmed and not ended, no suggestion open, the skill available in the owner's settings, and every attendee's card supporting it. It should return a reason when not, such as "Maya's suggestion is still open", so the button says why it is off, never greyed silently (issue #95).
2. **A typed change and a start.** A value for one change (new time, new activity, or a friend to add, who must be the suggester's friend) and a `begin`-style call that returns the interaction to save and the `SkillRequest` to start. The call names the plan's revision and checks everything again at the tap, as `ChainPlanner.begin` does. The app saves the interaction, applies `.started`, and starts the service, as for any chained link.
3. **The card's words.** For an incoming suggestion, the friend's name comes from the owner's nicknames, never from peer text: "Maya suggests 8:30 PM instead of 8 PM", "Maya suggests adding Jake", "Maya suggests a walk instead of boba". This could be a copy function over the proposal and the current plan, like `PickAPlaceCopy`. Accept and decline go through the usual `OwnerAnswer` on the proposal revision, and a decline looks like silence.
4. **Endings.** A distinct way for the suggester's card to tell "it didn't go through" (declined by someone, or the window closed) from the owner withdrawing it, so the card can say "The plan stays as it was" and name nobody. An `EndReason` the app maps, for example.
5. **Applying an agreed change.** The parent plan updated on every phone, with its revision one higher. Ideally this works like Pick a place: the change interaction produces the updated `Plan`, and a function like `ChainPlanner.parent(_:updatedBy:)` returns the parent to save. The coordinator saves it with `LifecycleCoordinator.update`. The invitees' phones need the same, from their invitee interaction's checked `chainedFrom`.
6. **Leaving.** A call the app makes when the owner taps "Leave this plan": the leaver's plan ends withdrawn after its conversation is retired. Then an event or produced plan for the others' phones gives the smaller roster, and a plan left with one person ends.
7. **Adding a friend.** How the added friend's Invite is sent once everyone agrees (by which phone, in which conversation), and that the roster goes only under the people topic, so the app can show the right consent sheet and audit.

**Meanwhile.** Lane A builds the UI against whatever lane E names here. After an agreed change, the app offers "Update in Calendar": EventKitUI's editor pre-filled with the new details. It needs no calendar permission, but cannot edit the event added before, so the sheet says to remove the old one (ADR 0018).

## 7. List Change the plan in Phase 1.5's flags (Orchestrator): resolved

Done in PR #115; the app's own line is gone.


**What.** Add `.changePlan` to `SkillFlags.phase1_5` in `Packages/StarlingCore/Sources/StarlingCore/SkillRegistry.swift`.

**Why.** The app runs no service for a skill whose flag is off (ADR 0206 decision 1), and `ChainPlanner.changeOffer` offers nothing for a skill that is unavailable, so with Core's flags as they are, "Suggest a change" never appears.

**Meanwhile.** The app's compositions add it themselves (`LiveServices.flags`). Once Core lists it, that line goes.


## 8. Plan change holds the app can watch (Orchestrator, ADR 0023): resolved

Done in PR #120 (d320371): `PlanChangeHolds.updates()`. The app creates the actor, follows its updates, and passes it to lanes D and E as `any PlanChangeHolding`.


**What.** In PR #120, let the app learn when a hold starts or ends, for example `PlanChangeHolds.holders: AsyncStream<[ConversationID: ConversationID]>` (each plan's holder by origin, sent after every hold and release that changes something), or an `onChange` callback. Lanes D and E take the holds as `any PlanChangeHolding`, not the concrete actor, so a test can pass its own.

**Why.** ADR 0023 decision 6 has lane A word a friend's card for a second change: no yes, and the line "Another change to this plan is in progress". The card and "Suggest a change" are drawn synchronously on the main actor, and `holder(of:)` can only be asked. If the app asks after every interaction update, a skill that releases its hold after reporting the ending leaves the next card without a yes until something else on the phone changes. Polling would fix that but wakes the phone for nothing.

**Meanwhile.** The app keeps each plan's holder on `AppModel` and asks `holder(of:)` for every standing plan after each interaction update and after each answer or start the owner taps. A card can stay without its yes until the next update.
