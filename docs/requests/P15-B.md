# Requests from lane P15-B (Down for... skill and the model)

## 1. Remove Phase 1 Down once the app runs Down for... (Orchestrator, lanes A and F)

**What.** When lane A wires `DownForService` in place of `DownNegotiator`, and the simulator's Down integration tests (`Tools/Simulator/Tests/DownIntegrationTests`) move to it:

- Core: remove `DownService`, `DownIntent`, `DownLevel`, `DownMatch`, `DownEndReason`, `DownEvent` (`Packages/StarlingCore/Sources/StarlingCore/Down.swift`) and `StarlingFakes.ScriptedDownService` (`DownFakes.swift`). Keep `IssueKey.downLevel` only if a Phase 1 build still needs to decode; nothing in Down for... sends it.
- `Capability.down` can go with them: Down for... reads support from `AgentCard.skills`.
- P15-B then removes `DownNegotiator` and its profile, conversation, and configuration from `StarlingNegotiation` in a follow-up PR (ADR 0211).

**Why.** ADR 0010's consequence: the facade stays until lane B moves Down into its skill package, then it goes. Two Down implementations invite fixes to the wrong one.

**Meanwhile.** Nothing breaks: `DownNegotiator` is unchanged and still tested.

## 2. Wiring Down for... in the app (lane A)

**What.** The app composes the service like this (Core v2.1):

```swift
let outbox = Outbox(transport: secureLink, policy: policy, consent: consentCoordinator, observer: egress, sequences: sentSequences, ledger: ledger)
let downFor = DownForService(localPeer: me, outbox: outbox, model: agent, psi: psi, ledger: ledger, store: persistentRequestStore, pairedPeers: pairedPeers)
```

- The consent coordinator applies consent events from `Disclosure.interaction`: every Down for... send sets `OutboundContext.interaction`, including a member's sends in the starter's conversation (ADR 0011 amendment 15). There is no relay any more.
- Pass the same persistent `ConversationLedger` to the Outbox and the service (ADR 0021).
- Feed every `InboxEvent` to `handle(_:)`, including `hello`, so unsupported friends are left out by card.
- Create an invitee `Interaction` on `.incoming` (Invite mode); its card follows as `proposalReady`.
- Call `restore(_:)` at launch with the store's Down for... interactions, live and ended in the last 24 hours. Provide a persistent `DownForRequestStore` (the in-memory one forgets on restart); its records hold the owner's rules, so keep them in the same protected storage as the interaction store.
- Pass `pairedPeers` so only a paired friend's invitation shows.
- Show `DownFor.revealNote` ("If nobody's up for it, nobody sees you asked.") with Ask quietly, and `DownForService.unsupported(among:cards:)` for "Maya's Starling doesn't do this yet".
- Fall back to `ProposalTemplate.sentence(_:now:)` whenever `SkillModel.proposalText` throws (model unavailable, or the sentence failed its checks).
- `SkillModel.intent` returns `ParsedIntent.mode` when the owner's words ask for one, and for "everyone except Jake" returns `.everyoneExcept([])` with the left-out friends in `mentionedNames`; resolve those names to `PeerID`s before `Audience.resolve`. A group's name ("the climbing crew") also arrives in `mentionedNames`; match it against the owner's group names. See request 6.

**Why.** ADR 0210 decisions 15 to 22; ADR 0212.

## 6. Left-out friends and groups in `ParsedIntent` (Orchestrator)

**What.** `SkillModel` cannot see the friends list or the owner's groups, and `ParsedIntent` has one list of names, `mentionedNames`, meaning "with these". Proposed additive fields:

```swift
public struct ParsedIntent {
    // ...
    /// Names of friends the owner left out ("everyone except Jake").
    public let leftOutNames: [String]
    /// A group the owner named ("the climbing crew"), as written.
    public let groupName: String?
}
```

**Why.** ADR 0020 adds `everyoneExcept` and `group(GroupID)`, but the model can only report names. Today names carry both meanings by convention (request 2), which the app must know to read.

**Meanwhile.** The convention in request 2.

## 7. Who reports the owner's answers (Orchestrator, lanes A, C, D)

**What.** Lane A's coordinator (`LifecycleCoordinator.answer` and `withdraw` on `phase-1.5/a-shell`) applies `ownerAccepted`, `ownerPassed`, and `withdrawn` itself before it calls the service. Down for..., Find a time, and Pick a place also report them from their services, so the coordinator sees each twice and drops the second as invalid. Please settle it in ADR 0011, as amendment 13 did for `started`. Either the coordinator applies owner answers and services never report them (which matches how it already works), or the reverse.

**Why.** One rule for every skill; today the duplicate is harmless only because the coordinator drops it.

**Meanwhile.** Down for... keeps reporting them, like lanes C and D.

**Settled for passes** by ADR 0011 amendment 16 (b766af5): see request 9.

## 8. Attributing a member's consent sheet (lane A)

**What.** `LifecycleCoordinator.owner(interaction:conversation:)` uses `Disclosure.interaction` only when that interaction's conversation equals the send's. A Down for... member sends in the starter's conversation, which is never its own request's conversation, so the check falls back to the conversation and finds no interaction: the member's sheets would suspend nothing. Please trust `Disclosure.interaction` whenever it names a live interaction of the disclosure's skill.

**Why.** Core v2.1 added `OutboundContext.interaction` for exactly this case.

## 9. One interaction per friend, and passes through the service (lane A)

**What.** For ADR 0011 amendments 16 and 17, which lane B now builds on:
- For an Ask quietly request, create one initiator interaction per resolved friend, each with its own `ConversationID`, the same `SkillIntent`, and participants `[that friend]`, and call `start` for each. `DownForService.start` throws `DownForError.oneFriendPerQuietAsk` for a quiet ask with more than one friend. Group them under the request on Home for display only.
- On a card's pass, hide the card at once and call `answer(_:with: .pass)`; do not apply `ownerPassed` or retire the conversation. For a starter's card, Down for... reports `ownerPassed` when the card's window ends (15 minutes by default), after retiring the conversation (ADR 0210 decision 13).
- After one or more pair plans, offer to invite the matched friends as a group: a new Invite request with those friends, `chainedFrom` the plans if you like. The invitation carries the roster under `people` (ADR 0210 decision 20).

**Why.** ADR 0011 amendments 16 and 17; ADR 0210 decisions 1, 13, and 20.

**Done** in lane A's PR #73. Lane B's follow-up adds `DownForPassThroughCoordinatorTests` in `App/Features/Tests`, where the coordinator and the service meet. It drives a starter's pass through the real `LifecycleCoordinator` and `DownForService` and compares what the friend receives with silence. The Orchestrator assigned this test to lane B, so it lives in lane A's test target. It adds a file and changes nothing of lane A's.

## 10. An invitation's starter is waiting, in words (lane A)

**What.** While a Down for... invitation waits for friends, Home reads "Checking with 1 friend", the mutual-reveal line, because `Interaction` does not carry the send mode. For an invitation, say who it waits on, for example "Waiting for Riley to answer". The coordinator knows the mode from the `SkillRequest` it started, so it can keep it with the request group.

**Why.** Device test 2 (issue #95). The service shows an invitation's starter no card, and nothing about a friend's interest, until a friend says I'm in (ADR 0210 decision 20a). The status line should say so plainly. The "both down" card Oliver saw matches the Debug build's scripted Down for... demo, which proposed after two seconds whatever the mode. That demo now waits for an invitation too.
