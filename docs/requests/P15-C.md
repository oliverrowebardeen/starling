# Lane P15-C requests (Find a time)

Owner: Orchestrator. Consumers: P15-A (shell), P15-F (red team). Branch `phase-1.5/c-find-a-time`, built on Core v2 (`c07c036`). Nothing here blocks P15-C; each item says what the lane does meanwhile.

## For P15-A: wiring Find a time

### 1. Calendar permission: the access API and the purpose string

What lane A calls from Starling's pre-permission sheet (ADR 0013, decision 3; ADR 0220):

```swift
import StarlingAvailability

let calendar = EventKitCalendarStore()          // one per app
let access = CalendarAccess(store: calendar)

access.status              // CalendarAccessStatus: .notDetermined, .fullAccess, .writeOnly, .denied, .restricted
access.shouldShowSheet     // true only when the system alert can still appear
await access.request()     // call only from the sheet's "Continue"; returns the new status
```

- When the owner starts Find a time and `shouldShowSheet` is true, show the sheet, then call `request()` from "Continue". On `.denied`, show `FindATimeCopy.deniedFallback` ("No problem, your agent will ask you instead.") and start the skill anyway: it asks the owner.
- When `shouldShowSheet` is false, start the skill without a sheet. It reads the calendar if it can and asks the owner otherwise.
- Nothing else may call `request()`. The service never does, so a friend's request never raises the alert.

**Info.plist** (lane A owns `App/`): add the key `CalendarAccess.usageDescriptionKey` (`NSCalendarsFullAccessUsageDescription`) with `CalendarAccess.purposeString`:

> Starling checks when you're busy so friends' agents can find a time without asking you. Event details stay on your iPhone.

Without this key iOS 17 and later deny the request without showing the alert. Do not add `NSCalendarsUsageDescription` (pre-iOS 17) or any write-only key: Add to Calendar uses `EKEventEditViewController` and needs neither (ADR 0018).

**You › Skills:** store a `CalendarUse` (`.useMyCalendar` or `.justAskMe`, labels `FindATimeCopy.useMyCalendar` and `.justAskMe`) and show the permission line from `access.status`.

### 2. Building the service

```swift
let findATime = FindATimeService(
    localPeer: identity.peerID,
    outbox: outbox,                                    // the app's single Outbox
    pairedPeers: pairedPeerStore,
    availability: .standard(
        calendar: calendar,
        use: { await settings.calendarUse },           // You › Skills
        stated: { [] }                                 // optional: free windows the owner already stated
    ),
    checkpoints: FileFindATimeCheckpoints(directory: applicationSupport.appending(path: "FindATime")),
    isTurnedOn: { await settings.isOn(.findATime) }
)
```

Register `FindATimeSkill.descriptor` (not `SampleSkills.findATime`) in the registry. Feed it every `InboxEvent`, including `hello`s, because the policy needs each friend's card to know their model runs on-device. Call `restore(_:)` at launch before the first `handle(_:)`.

The proposal card's sentence: `FindATimeProposalWriter(model:localPeer:timeZone:nickname:).sentence(for:)`, which uses `SkillModel.proposalText` and falls back to a template.

### 3. The sheet's third line differs by role (needs a decision)

ADR 0013 fixes the sheet's rows, including "Priya sees: Only times you're both free". Without private set intersection, the starter must name times first, so that line is true for the friend who answers but not for the starter (ADR 0221, decision 9). Proposed:

| Role | Label | Value |
|---|---|---|
| Starting Find a time | "Priya sees" | `FindATimeCopy.PermissionSheet.seesValueWhenAsking`: "Only a few times you're free" |
| Answering a friend | "Priya sees" | `.seesValueWhenAnswering`: "Only times you're both free" |

The sheet appears when the owner starts Find a time, so the first row is the one it normally shows. **Needs:** Oliver's or the Orchestrator's agreement to amend ADR 0013, decision 3. Meanwhile the copy lives in `FindATimeCopy` and lane A can choose.

### 4. Who reports consent events

The service cannot see a consent sheet: `Outbox` calls the app's `ConsentProvider` directly. Find a time assumes this division, and its tests run a coordinator that follows it:

- The app's `ConsentProvider` applies `consentNeeded(request:)` before showing the sheet and `consentGiven(request:)` after an approval, finding the interaction by `Disclosure.conversation`.
- On a decline it applies nothing. `Outbox` throws `consentDeclined` to the service, which reports `ownerPassed` and ends.

**Needs:** the Orchestrator to confirm this in ADR 0011 or ARCHITECTURE section 8, so lanes A, B, C, and D report consent the same way. If lane A chooses to apply `ownerPassed` itself, Find a time's `ownerPassed` becomes a duplicate the coordinator drops; nothing breaks.

### 5. `planEnded`

Find a time reports `planEnded` when its plan's time has passed (while the app is running). If the coordinator also applies it, the second is dropped as invalid. Tell me if lane A prefers to own it.

## For the Orchestrator: Core and tools

### 6. Clearing consent requests that died with the app (Core, nonblocking)

A consent sheet open when the app quits never completes, so the stored `Interaction` stays in `awaitingConsent` with that request in `pendingConsents`. A fresh request after restart joins it, and the interaction resumes only when every request is approved, so it can never resume. Find a time's own copy treats such requests as given (ADR 0222, decision 5), but the coordinator's record stays stuck.

Proposed: `InteractionEvent.consentAbandoned(request: UInt32)`, valid in `awaitingConsent`, which removes the request and resumes when none remain; the coordinator applies it for every pending request at launch, before `restore(_:)`. Meanwhile: nothing in P15-C; lane A could do the same with a local rule.

### 7. Per-skill state on `Interaction` (Core, nonblocking)

`Interaction` has no place for state only the skill knows, so Find a time keeps its own `FindATimeCheckpointStore` (ADR 0222). Proposed for a later freeze: `Interaction.skillState: Data?` (bounded, opaque, never sent) and `SkillEvent.checkpoint(InteractionID, Data)`, so the coordinator persists it with the record and every skill restores the same way. Meanwhile: the local checkpoint store, which works today.

### 8. The release check should also look for `StarlingAvailabilityFakes`

`Tools/check-release-no-fakes.sh` greps for `StarlingFakes` symbols. `StarlingAvailabilityFakes` (the calendar store double with event details) does not match that pattern. Proposed: grep for `Fakes` module names generally, or add `StarlingAvailabilityFakes`. Meanwhile: the app should depend only on the `StarlingAvailability` product.

### 9. `SampleSkills.findATime` and the people topic

The real descriptor adds `.people` to `topicsUsed`, because a group plan sends its roster (ADR 0012, amendment 8; ADR 0014). `SampleSkills.findATime` lacks it. Proposed: add `.people` to the sample, so lane A's previews match. Nonblocking.

### 10. Envelope sequence numbers restart at 0 after an app restart (Core)

`Outbox` keeps `nextSequence` per conversation in memory, so a relaunched app sends its next envelope in a live conversation with sequence 0. The friend's `Inbox` has already seen 0 in that `(sender, conversation)` and drops it, and every following number it has seen, as `.replay`. Find a time's restore tests pass only because retries keep raising the sequence until it passes the highest one the friend saw (`RestoreTests.aStarterResumesAfterSayingThatWorks`, where the first confirmations after the restart are dropped). A conversation that had sent more envelopes than a step's retries would stall until its deadline.

Proposed: start each conversation's sequence at a value that cannot repeat across launches, for example milliseconds since 1970 at the first send, then +1. `Inbox` already accepts gaps and needs no change. Meanwhile: retries in Find a time.

### 11. Threat model additions

For `docs/THREAT_MODEL.md`:

- A starter shows each friend up to 16 times it is free; with a calendar, the gaps show busy time in the range (never why). A friend who keeps sending requests learns 16 answers per request, at most 4 open requests at a time. Private PSI would remove this. (ADR 0221)
- A pass, "no times work", a calendar with no overlap, and a declined consent sheet are the same `reject(noOverlap)` on the wire.
- Find a time checkpoints hold candidate times, friends' answers, and peer IDs at rest, with complete file protection on iOS, until the interaction ends. (ADR 0222)
- Over an unauthenticated transport, a forged answer under a friend's ID is refused if it names a time that was not offered; the secure channel is what rejects the forgery itself.
