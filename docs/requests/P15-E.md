# Lane P15-E requests (Chaining and audit)

Owner: Orchestrator. Consumers: lane A (shell and coordinator), lane F (red team). Built against Core v2 at c07c036. None of these blocks P15-E; each has a local workaround in `Packages/StarlingChaining`.

## 1, 2, and 2b. Resolved in Core v2.1 (753ddcf, PR #57)

- **1, the policy's items for a send it allowed:** `PolicyEngine.disclosedItems(for:)` and `OutboxObserver.outbox(didSend:context:decision:disclosed:)`. `EgressRecorder` records Outbox's `disclosed`, and `ChainedFromPolicy` passes the wrapped policy's items through. The `DisclosedItemsForSend` function is gone.
- **2, a friend's `chainedFrom` hint:** `Interaction.friendChainHint` and `setFriendChainHint(_:)`. `PlanTimeline` reads it; the `friendHints` map is gone.
- **2b, an envelope ID and unknown-items flag:** `EgressRecord(message:itemsUnknown:)`, `Interaction.record` ignoring a repeat, and `Interaction.egressIsKnown`. The marker item and `StoreEgressSink`'s in-memory IDs are gone.

## 2c. Core: the plan revision a suggestion changes (ADR 0243)

**What.** An optional field naming the plan revision an offer is based on, for example `Proposal.basedOnRevision: UInt32?` (absent on every other skill's offers).

**Why.** ADR 0022 says a suggestion names the plan revision it changes. Change the plan carries it in `Proposal.round` for now, because a new issue key would put a consent sheet in front of every send (the policy asks about any issue no topic covers). That caps a plan at 15 changes (`ChainPlanner.maxChangeableRevision`). Tests: `SafetyTests.aSuggestionMayaCannotTrustOpensNothing` (a wrong revision opens nothing).

**Meanwhile.** `round` carries the revision, and "Suggest a change" is not offered past revision 14.

## 2d. Core: the asked-roster digest, for Change the plan and Pick a place

**What.** Move `ChangePlanService.rosterDigest(origin:revision:suggester:asked:)` into StarlingCore, for example as `Plan.askedDigest(revision:organizer:asked:) -> MessageID` or a free function next to `Plan`.

**Why.** The Orchestrator's follow-up after PR #111: lane D adds it to Pick a place requests chained from a plan, and StarlingChaining then accepts a friend's narrowed place result when the digest equals this phone's whole roster. Both skill packages depend only on StarlingCore, and StarlingChaining is not a library dependency of either, so Core is the one place both can use without a new sideways dependency.

**Meanwhile.** It lives in `StarlingChangePlan` (public), and a friend's place result applies only with the plan's whole roster.

## 3. Resolved: who applies `.started` for an initiator

Orchestrator, 2026-10-01: the lifecycle coordinator applies `.started` when the owner sends, before calling `SkillService.start`; a service never applies it for an initiator. Swap photos no longer emits it.

## 4. Lane A: wiring (no interface change)

1. Install `EgressRecorder(sink: coordinator, journal: onDiskJournal)` as the Outbox observer, with an `EgressJournal` kept in a file on the phone (each `remember` and `forget` durable before it returns, and throwing when it cannot be), and call `recover()` at launch before showing any plan detail. The recorder notes each send in `willSend`, so a journal that cannot write stops the send; implement `EgressSink.appendEgress(_:conversation:interaction:)` in the coordinator (the interaction is the one the send named, kept in the journal, so it survives a crash; prefer it over any in-memory lookup) with `Interaction.record`, which ignores a repeat (the recorder retries a write that threw). Call `interactionArrived(conversation:)` right after saving any new interaction (a skill may send before its incoming announcement is consumed), `retryPending()` when the store recovers, and pass `unconfirmedConversations` to `PlanTimeline` so "What left your phone" says when it cannot confirm; if `journalUnreadable`, show no Kept list at all. If lane G's `InMemoryAuditLog` stays installed, add a small fan-out observer.
2. Wrap the app's policy: `ChainedFromPolicy(wrapping: rulesPolicy, store: store)`. It forwards `disclosedItems(for:)`, so the audit still gets the policy's items.
3. A friend's request (`SkillEvent.incoming` with `chainedFrom`): call `IncomingChain.timelineParent`, then `setFriendChainHint` with its result; never a `ChainLink`.
4. It's a plan: rows from `ChainPlanner.suggestions`; when `needsConsent`, a sheet listing `adds` (topics and permissions) before `begin` or `optIn`; save `ChainStart.interaction`, apply `.started`, then call the service's `start(request)`. The request carries the skill's default send mode and goes only to the parent plan's attendees. Show a waiting after-plan-ends link as the plan's "Photos after" chip, not under In progress.
5. Run `PlanEndScheduler` while the app is open and call `due()` at launch and on foreground. For each result, inside the same serialized write that applies the event, first confirm it with `ScheduledChain.isCurrent(storedLink)` (or `PlanEndScheduler.claim`, when the read and the write are not already serialized), and drop it if that returns false: the owner may have opted out, or the link may have started, after the hand-over. Then on `.start`, apply `.started` to `due.link` (its participants narrowed to the plan's current attendees), save it, and call the service with `due.request(...)`; on `.cancel(link, event)`, apply `event`. Schedule a local notification at `nextEnd(after:)`.
6. After applying any event to a Pick a place interaction, this phone's own link or a friend's request, save `ChainPlanner.parent(updatedBy: link, in: interactions)` if it returns one (review of PR #118). It finds the stored plan itself: through `link.chain` for an own link, through `friendChainHint` for a friend's request, which has no chain. Replace the `link.chain?.parent` lookup in `AppModel.updateParent(of:)` with it. It applies the agreed place and the agreed, possibly shorter, roster, once both are in and only over the plan's revision just before the one the result names, so calling it after every event is safe.
7. Plan detail: `PlanTimeline` and its `whatLeft`; add hand-offs (Add to Calendar) as rendered rows.
8. Build `SwapPhotosService(outbox:ledger:me:planLookup:)` with the same `ConversationLedger` the Outbox uses. Call its `retryRetirements()` when storage recovers.
9. Swap photos question: present `SwapPhotosPicker` and pass its `OwnerAnswer` to the service. Swap photos needs no Info.plist purpose string (ADR 0242).

### Change the plan (ADR 0243)

10. Register `ChangePlanService(outbox:ledger:journal:me:planLookup:resend:now:sleep:)` with the Outbox's ledger and a `ChangePlanJournal` kept on disk (each save and remove durable before it returns, and throwing when it cannot be: the service then holds or refuses the step). Call `restore` with every stored interaction at launch, after the store loads: it brings back yeses, commits, applied changes, and departures, and replays any plan update the store never saved. `answer` (a yes) and `start` (a leave) can throw `ChangePlanError.journalUnavailable`; show the card or plan unchanged. Pass friends' `hello` envelopes to it like any other, so it learns their cards. `planLookup` returns the standing plan whose `Plan.origin` is the conversation, with the interaction that holds it (`PlanRef`).
11. "Suggest a change" on the plan's detail: `ChainPlanner.changeOffer(for:in:settings:cards:now:)`, a sheet for its `adds` when `needsConsent`, then `PlanChange.encoded(for:)` and `beginChange(...)` (with `ChangePlan.defaultExpiry(for:now:)`); save, apply `.started`, call `start`. "Leave this plan": `beginLeave(...)` with `PlanChange.leave.encoded(for:)`.
12. Apply the service's `.produced(_, .plan(...))` and `.lifecycle(_, .withdrawn)` events to the interaction they name: it is the plan's own interaction, not the change's.
13. A change that ends planned updated the plan: show it on the plan's timeline, not as a plan of its own. A suggester's change that ends with nobody up reads "The plan stays as it was", naming nobody. For a friend being added, the change interaction holds the plan once it is planned.
14. Swap photos' and Pick a place's plan lookups should also match by `Plan.origin` (`Interaction.planConversation`), so a friend who joined later can be part of them.
15. Apply a `.plan` artifact to an interaction only if its revision is exactly one above the stored plan's (or it equals the stored plan): a compare-and-set that serializes plan changes from different skills (Codex review of PR #111, finding C). After applying any plan update, call `ChangePlanService.planDidChange(plan.origin)`.
16. Call `ChainPlanner.parent(updatedBy:in:)` (item 6) for this phone's own place links and for friends' grouped ones: this phone's own link narrows the plan to those who accepted; a friend's applies only with the plan's whole roster and never removes anyone.

## 5. Lane F: scenarios to cover

- A peer's envelope with `chainedFrom` naming a plan it was not in, a conversation that never became a plan, or a real plan: expect at most an invitee interaction, never a start, picker, permission, or schedule.
- A chained skill's service that omits or forges `chainedFrom`: expect `chain.chained_from_mismatch` denial and no egress record.
- A Swap photos offer with extra issues, a count over 24, or from someone outside the plan: expect it dropped.
- Core v2.1: a chained request never reaches anyone outside the parent plan's attendees, even one the parent asked (ADR 0020 decision 9.3); a Swap photos offer sent as a quiet ask is ignored; a retried Swap photos offer after the friend passed never shows the card again, including after a restart.

## 6. Threat model additions

- `chainedFrom` is peer-controlled; it only groups on the timeline (ADR 0240 decision 7).
- Swap photos sends a photo count under the photos topic; no photo bytes travel in Phase 1.5 (ADR 0242).
