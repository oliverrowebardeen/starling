# Lane P15-E requests (Chaining and audit)

Owner: Orchestrator. Consumers: lane A (shell and coordinator), lane F (red team). Built against Core v2 at c07c036. None of these blocks P15-E; each has a local workaround in `Packages/StarlingChaining`.

## 1, 2, and 2b. Resolved in Core v2.1 (753ddcf, PR #57)

- **1, the policy's items for a send it allowed:** `PolicyEngine.disclosedItems(for:)` and `OutboxObserver.outbox(didSend:context:decision:disclosed:)`. `EgressRecorder` records Outbox's `disclosed`, and `ChainedFromPolicy` passes the wrapped policy's items through. The `DisclosedItemsForSend` function is gone.
- **2, a friend's `chainedFrom` hint:** `Interaction.friendChainHint` and `setFriendChainHint(_:)`. `PlanTimeline` reads it; the `friendHints` map is gone.
- **2b, an envelope ID and unknown-items flag:** `EgressRecord(message:itemsUnknown:)`, `Interaction.record` ignoring a repeat, and `Interaction.egressIsKnown`. The marker item and `StoreEgressSink`'s in-memory IDs are gone.

## 3. Resolved: who applies `.started` for an initiator

Orchestrator, 2026-10-01: the lifecycle coordinator applies `.started` when the owner sends, before calling `SkillService.start`; a service never applies it for an initiator. Swap photos no longer emits it.

## 4. Lane A: wiring (no interface change)

1. Install `EgressRecorder(sink: coordinator, journal: onDiskJournal)` as the Outbox observer, with an `EgressJournal` kept in a file on the phone (each `remember` and `forget` durable before it returns, and throwing when it cannot be), and call `recover()` at launch before showing any plan detail. The recorder notes each send in `willSend`, so a journal that cannot write stops the send; implement `EgressSink.appendEgress(_:conversation:)` in the coordinator with `Interaction.record`, which ignores a repeat (the recorder retries a write that threw). Call `retryPending()` when the store recovers, and pass `unconfirmedConversations` to `PlanTimeline` so "What left your phone" says when it cannot confirm; if `journalUnreadable`, show no Kept list at all. If lane G's `InMemoryAuditLog` stays installed, add a small fan-out observer.
2. Wrap the app's policy: `ChainedFromPolicy(wrapping: rulesPolicy, store: store)`. It forwards `disclosedItems(for:)`, so the audit still gets the policy's items.
3. A friend's request (`SkillEvent.incoming` with `chainedFrom`): call `IncomingChain.timelineParent`, then `setFriendChainHint` with its result; never a `ChainLink`.
4. It's a plan: rows from `ChainPlanner.suggestions`; when `needsConsent`, a sheet listing `adds` (topics and permissions) before `begin` or `optIn`; save `ChainStart.interaction`, apply `.started`, then call the service's `start(request)`. The request carries the skill's default send mode and goes only to the parent plan's attendees. Show a waiting after-plan-ends link as the plan's "Photos after" chip, not under In progress.
5. Run `PlanEndScheduler` while the app is open and call `due()` at launch and on foreground. For each result, inside the same serialized write that applies the event, first confirm it with `ScheduledChain.isCurrent(storedLink)` (or `PlanEndScheduler.claim`, when the read and the write are not already serialized), and drop it if that returns false: the owner may have opted out, or the link may have started, after the hand-over. Then on `.start`, apply `.started` and call the service with `due.request(...)`; on `.cancel(link, event)`, apply `event`. Schedule a local notification at `nextEnd(after:)`.
6. When a link finishes Pick a place, save `ChainPlanner.parent(_:updatedBy:)`.
7. Plan detail: `PlanTimeline` and its `whatLeft`; add hand-offs (Add to Calendar) as rendered rows.
8. Build `SwapPhotosService(outbox:ledger:me:planLookup:)` with the same `ConversationLedger` the Outbox uses.
9. Swap photos question: present `SwapPhotosPicker` and pass its `OwnerAnswer` to the service. Swap photos needs no Info.plist purpose string (ADR 0242).

## 5. Lane F: scenarios to cover

- A peer's envelope with `chainedFrom` naming a plan it was not in, a conversation that never became a plan, or a real plan: expect at most an invitee interaction, never a start, picker, permission, or schedule.
- A chained skill's service that omits or forges `chainedFrom`: expect `chain.chained_from_mismatch` denial and no egress record.
- A Swap photos offer with extra issues, a count over 24, or from someone outside the plan: expect it dropped.
- Core v2.1: a chained request never reaches anyone outside the parent plan's attendees, even one the parent asked (ADR 0020 decision 9.3); a Swap photos offer sent as a quiet ask is ignored; a retried Swap photos offer after the friend passed never shows the card again, including after a restart.

## 6. Threat model additions

- `chainedFrom` is peer-controlled; it only groups on the timeline (ADR 0240 decision 7).
- Swap photos sends a photo count under the photos topic; no photo bytes travel in Phase 1.5 (ADR 0242).
