## Core v2.1 update

The branch is rebased onto `753ddcf`. PR #50 remains a draft by the
Orchestrator's instruction. The contract pass is complete work, not a blocker;
real-service adapters follow each lane's merge in issue #49.

New executable cases cover:

- All four sample skills use required send modes. Malformed and missing modes,
  mode without a skill, and retired version 1 fail at the codec and Inbox before
  reserving a sequence. Valid v2 and legacy v0 frames are positive controls.
- Quiet mode can be declared only by a mutual-reveal skill. Audience resolution
  respects explicit exceptions even with alwaysInclude, unknown groups resolve
  to nobody, quietOnly differs by mode, and explicit picked friends override
  standing rules as ADR 0020 requires. Pairing and skill support still filter.
- Never blocks new owner values while exact subsets of trusted query candidates
  can pass under every privacy choice. Seven value shapes cover changed slots,
  currency, coordinates, peer IDs, counts, flags, and added keywords.
  Cloud-model consent remains required; missing or mismatched local context
  cannot turn a private value into an allowed answer.
- Location and calendar details have separate topics and defaults. Budget,
  diet, location, and calendar details can remain local without blocking the
  sample Find a time or Pick a place descriptors.
- A denied invitee acceptance ends blockedByPrivacy from proposed, confirmed,
  or consent-suspended states. An already planned interaction stands.
- Consent cancellation closes only the named pending request, never reopens a
  completed request, and preserves content and high-water marks after restart.
  The actual app ConsentCoordinator is tested with cancelled sends. Its
  remembered approvals are isolated by Disclosure.interaction as well as skill
  and conversation.
- Denied, declined, and cancelled sends leave no sequence gap or successful-send
  audit entry. A persisted sequence store continues across a backward clock;
  storage failure and exhaustion fail closed. Unknown audit items remain
  unknown after a restart and duplicate message records are idempotent.

Important remaining service checks, not claimed by the above contract tests:

- No request traffic to excluded recipients, not-down-equivalent inbound quiet
  responses with the same timing, and chains confined to parent attendees.
- Mode validation before a real service handles an incoming envelope, and no
  mid-conversation switch from quiet to invite.
- Mapping Never-caused refusals to noOverlap rather than policy, enforcing the
  cumulative 16-candidate limit per issue/conversation, and binding answering
  context to the actual query ID, sender, conversation, and current step.
  Query itself contains only issue and candidates; Core's trusted local context
  cannot establish this provenance for a service.
- Dropping an old send's denial/failure after a newer proposal, coordinator-only
  started/consent/planEnded events, queued progress during consent, and restoring
  recently ended conversations as tombstones for 24 hours.

No shared production change is requested. These cases and their reproductions
are tracked in issue #49. No new product defect was inferred from the absent
real implementations, and issue #46 remains the focused known failure.

## 3. Threat-model clarification for the Orchestrator

Consider carrying these existing limitations into the Phase 1.5 threat model:
authenticated peers can still send malicious skill refs and `chainedFrom` hints;
authentication never authorizes a local skill or permission. Inbox replay state
does not survive restart, and Core lifecycle checks cover lifecycle events but
not arbitrary coordinator artifact updates. Real service/coordinator recovery
must enforce the remaining boundaries. This lane does not edit the threat model.
