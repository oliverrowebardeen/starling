# Requests from lane P15-G (pairing reliability)

No Core change is needed. These are for the Orchestrator and lane P15-A.

## 1. Threat model additions (Orchestrator)

From ADR 0260, for `docs/THREAT_MODEL.md`:

- **A ceremony gives out one nonce, so one code.** A phone in the middle of two victims, the responder to both, learns each victim's code from that victim's message 3. Once a phone has sent its nonce, a request to start over ends its ceremony visibly instead of restarting it, so every further try needs a new ceremony and shows a failure on the victim's screen. A sheet rejoins on its own at most once (ADR 0260, review round 3 of #104).
- **A third phone in range can restart or end a pairing.** Before this phone's nonce goes out, it can restart one with a forged hello for a new attempt, or end one with an abort naming the current attempt, using IDs it overheard. After the nonce, a forged hello ends the ceremony visibly. It learns no code either way. This is denial of service only, the same class as the unauthenticated abort ADR 0101 already allowed, and anyone jamming the radio can do the same. Once a code is shown, nothing unauthenticated changes it.
- **Pairing requests are unauthenticated claims.** The sheet joins a request automatically. A forged request can at most start a ceremony whose code will not match the real friend's.
- **A finished ceremony replays its last encrypted messages** up to 3 times. They are the same ciphertexts already sent, so a replay reveals nothing new.
- **Wi-Fi Aware roles.** A forged link hello from an OS-paired device can make a phone settle a role that stops the link until the next genuine hello. This is denial of service, and only devices the owner paired in person can try it (as in ADR 0110).
- **Device names seed a nickname suggestion.** They come from the other phone and are attacker-controllable (ADR 0102). The owner confirms the name, and NicknameCheck warns about look-alikes.

## 2. ADR index and superseded decisions (Orchestrator)

ADR 0260 amends the following. Please add its row and note these in the index:

- ADR 0101 decision 2: link loss no longer ends a ceremony.
- ADR 0110 decision 3: symmetric roles become fixed roles.
- ADR 0145 decisions 2 and 4: `PairingRoute` is gone; one service runs over every link.
- ADR 0202 decision 3: notifications are offered after the first friend.

## 4. Lane P15-F: one red-team test uses the old pairing names

`Tools/Simulator/Tests/Phase15RedTeamTests/CapabilityAndRosterAttackTests.swift`, `peerChosenNameMustNotBecomeOwnerNicknameWithoutReview`, reads `PairingModel.selected`, `.nickname`, and `.suggestedName`. ADR 0260 renamed them to `phone` and `name`. The name is now asked after the codes match, and the pin is saved under "New friend" until the owner taps Done.

Meanwhile a small extension at the end of `PairingModel.swift` maps the old names, and the test passes unchanged. Please move the test to the new names, and consider asserting the new invariant directly: after pairing, the pin's nickname is `PairingModel.placeholderName`, and only `saveName()` changes it. Then lane G removes the extension.
